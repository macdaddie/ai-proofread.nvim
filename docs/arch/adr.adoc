Superseded decisions shall not be deleted.

=== ADR-024: Phase 3 Inference and Presentation Implementation

Status:: Accepted
Date:: 2026-11-16

==== Context

Phase 3 completes the plugin with inference integration and
user-facing presentation via Neovim's quickfix list.

Required components:

* Ollama adapter for HTTP requests and JSON response handling
* Review controller for orchestration
* Quickfix presenter for result display

==== Decision

Implement Phase 3 modules in Lua:

* `lua/ai-proofread/ollama.lua` - Ollama HTTP adapter
* `lua/ai-proofread/review_controller.lua` - Chunk orchestration
* `lua/ai-proofread/quickfix.lua` - Quickfix list generation

==== Rationale

* `vim.system()` with `curl` avoids external Lua HTTP libraries
* Sequential chunk processing matches context window constraints
* Quickfix list provides native Neovim navigation and display
* Stale result detection prevents showing outdated findings

==== Implementation Details

===== Ollama Adapter

* `validate_endpoint(url)` - Check Ollama service availability
* `model_available(url, model)` - Verify configured model is installed
* `build_request(...)` - Construct API request payload
* `send_request(url, payload, timeout_ms)` - Send inference request
* `extract_findings(response)` - Decode JSON twice (transport → findings string → findings object)

===== Review Controller

* `create_request(buffer_number, filetype, config)` - Build review request
* `review(request)` - Process all chunks sequentially
* `build_prompt(text, config, context)` - Construct Ollama prompt
* `buffer_changed(state)` - Detect stale results

===== Quickfix Presenter

* `build_entry(finding, buffer_number)` - Convert finding to quickfix entry
* `build_quickfix_list(findings, buffer_number)` - Sort entries by location
* `show(entries, title, auto_open)` - Populate and open quickfix list

==== Consequences

* Plugin supports full review workflow from buffer to results
* Results displayed in Neovim's native quickfix window
* Partial failures handled gracefully with incomplete status

==== Next Steps

Continue with Phase 4 (health checks, configuration, commands) and Phase 5 (benchmark corpus)

=== ADR-025: Plugin Configuration and Commands

Status:: Accepted
Date:: 2026-11-17
Revised by:: ADR-029

==== Context

The plugin requires a stable public interface that works
with standard Neovim package managers without manager-specific
runtime code.

==== Decision

Expose `setup()`, `review()`, `cancel()` and `health()` from
the root Lua module.

Register `AIProofread`, `AIProofreadCancel` and
`AIProofreadHealth` from the standard `plugin/` entry
point.

Keep user configuration in Lua and provide defaults for the
local Ollama endpoint, model, supported filetypes, chunk
limits, quickfix behaviour and review keymap.

==== Consequences

The same repository layout supports `vim.pack`, lazy.nvim,
native packages and other standard Neovim package managers.

Configuration does not contact Ollama. Health checking and
review execution remain explicit user actions.

=== ADR-027: Tested Asynchronous Plugin Structure

Status:: Accepted
Date:: 2026-11-17
Supersedes:: ADR-024

==== Context

ADR-024 described the first inference and presentation
implementation. Testing exposed circular module loading,
blocking process waits, invalid JSON error handling and
inconsistent source-coordinate contracts.

The implementation was rebuilt and verified with headless
Neovim tests and a real Ollama review.

==== Decision

Use the following runtime modules:

* `init.lua` for the public API and configuration state.
* `controller.lua` for sequential review lifecycle,
  cancellation, stale-result rejection and aggregation.
* `ollama.lua` for asynchronous `vim.system()` transport and
  protected JSON decoding.
* `adapters.lua` and `markup.lua` for source-preserving
  chunking and length-preserving masking.
* `locator.lua` and `validate.lua` for deterministic finding
  validation and source coordinates.
* `prompt.lua`, `schema.lua` and `quickfix.lua` for their
  corresponding bounded responsibilities.

The controller shall process one chunk at a time and retain
the active process handle for cancellation.

Every chunk shall map each review-text byte to an absolute
captured-buffer byte. Quickfix positions shall be derived as
line-local byte columns with verified end positions.

Ollama requests shall remain asynchronous and shall include
`stream: false`, `think: false`, temperature zero and the
packaged JSON Schema.

==== Rationale

* Prevents inference from blocking Neovim.
* Removes circular module dependencies.
* Keeps probabilistic output behind deterministic validation.
* Makes cancellation and stale-result handling testable.
* Preserves source coordinates through markup masking.
* Supports clean installation through standard package managers.

==== Consequences

The modules named in ADR-024 are historical and no longer
describe the runnable implementation.

The headless suite is the executable specification for the
critical review workflow. Real Ollama integration verifies
that precise model quotations reach quickfix correctly.

Typst and RTF remain deferred until dedicated parsers provide
the same reversible mapping guarantees.

== Historical Decisions

=== ADR-001: Native macOS fm Integration

Status:: Superseded
Date:: 2026-11-16
Superseded by:: ADR-014

==== Original Context

The original architecture required a custom Swift
command-line application to access Apple's Foundation
Models framework.

The native macOS `fm` utility appeared to remove
the need for that helper.

==== Original Decision

Use the native `fm respond` command instead of
a custom Swift executable.

==== Original Rationale

* Avoid a compiled helper.
* Reduce installation complexity.
* Retain local inference.
* Use structured generation.
* Minimise dependencies.

==== Supersession

Comparative testing demonstrated that the available
on-device model did not provide adequate proofreading
accuracy for the intended application.

The decision to avoid a custom Swift executable remains
valid, but `fm` is no longer the selected inference
interface.

=== ADR-002: Lua-Only Plugin Implementation

Status:: Accepted
Date:: 2026-11-16

==== Context

Neovim provides native Lua APIs for buffer management,

==== Decision

Implement all project-specific application logic in Lua.

==== Rationale

* Native Neovim integration.
* Minimal dependencies.
* Straightforward maintenance.
* Familiar plugin architecture.
* No additional application runtime language.

=== ADR-004: Structured JSON Generation

Status:: Accepted
Date:: 2026-11-16
Revised by:: ADR-016

==== Context

Free-form model responses are difficult to convert
reliably into editor diagnostics.

==== Decision

Use structured JSON output with a versioned findings schema.

==== Rationale

* Predictable response structure.
* Simplified Lua parsing.
* Easier validation.
* Improved testability.
* Separation of inference and presentation.

==== Consequences

The schema shall be supplied through Ollama's structured
output interface.

ADR-034 extends this requirement to native `fm`, which
supplies the packaged schema through `--schema`.

Schema compliance does not guarantee correctness.

All findings require additional deterministic validation.

=== ADR-007: Non-Destructive Review

Status:: Superseded
Date:: 2026-11-16
Superseded by:: ADR-029

==== Context

Generative models may suggest inappropriate corrections
or changes to technical meaning.

==== Decision

The plugin shall never modify source buffers automatically.

==== Rationale

* Preserves authorial control.
* Prevents accidental document corruption.
* Simplifies the initial implementation.
* Avoids complex edit reconciliation.

==== Consequences

The author applies corrections manually.

Selective correction application may be considered
in a later release.

=== ADR-008: Deterministic Source Validation

Status:: Accepted
Date:: 2026-11-16

==== Context

Language models may produce incorrect line numbers,
columns or text offsets.

Markup and Unicode increase this risk.

==== Decision

Use the model to identify issues and offending text.

Use Lua to validate and locate findings in the
original buffer snapshot.

==== Rationale

* Prevents fabricated source positions.
* Supports accurate quickfix navigation.
* Handles Unicode through explicit byte offsets.
* Separates inference from deterministic logic.

==== Consequences

Ambiguous or unverifiable findings shall not receive
fabricated quickfix locations.

Rejected findings shall be counted and reported.

=== ADR-009: On-Device Inference Only

Status:: Superseded
Date:: 2026-11-16

==== Original Context

Document review may involve private or unpublished material.

The original architecture used Apple's on-device model.

==== Original Decision

Use the on-device system model exclusively.

Documents may exceed the configured model context.

==== Decision

=== ADR-011: Buffer Snapshot Consistency

Status:: Accepted
Date:: 2026-11-16

==== Context

The author may continue editing while a review is running.

Findings generated against an earlier document state
may become invalid.

==== Decision

Capture the buffer changedtick and source snapshot
when a review begins.

Discard results if the buffer changes before publication.

==== Rationale

* Prevents stale diagnostics.
* Protects source-location accuracy.
* Avoids misleading quickfix navigation.

==== Consequences

The author may need to repeat a review after editing.

Incremental reconciliation is deferred.

=== ADR-012: No Custom Language Server

Status:: Accepted
Date:: 2026-11-16

==== Context

The plugin resembles a language diagnostic tool but
does not require continuous document analysis.

==== Decision

Do not implement the Language Server Protocol.

==== Rationale

* Avoids unnecessary infrastructure.
* Simplifies implementation.
* Preserves manual review semantics.
* Allows direct quickfix integration.

==== Consequences

The plugin shall not expose itself as an LSP server.

Optional diagnostics integration may be added later
without implementing the LSP protocol.

=== ADR-013: Isolated Inference Adapter

Status:: Accepted
Date:: 2026-11-16

==== Context

Inference interfaces and model capabilities may change.

The document-processing and presentation components
should not depend on a particular inference transport.

==== Decision

Isolate inference execution behind a Lua adapter.

The review controller shall not depend directly on
HTTP request construction or provider-specific responses.

==== Rationale

* Contains inference-specific behaviour.
* Simplifies testing through mock responses.
* Supports model changes.
* Avoids coupling document logic to transport.

==== Consequences

The adapter introduces a small abstraction boundary.

Alternative providers are not required for the
initial release.

== Current Decisions

=== ADR-014: Local Ollama Inference

Status:: Superseded
Date:: 2026-11-16
Supersedes:: ADR-001, ADR-009
Superseded by:: ADR-034

==== Context

The original architecture selected Apple's native
Foundation Models interface through the `fm` CLI.

Subsequent local testing compared eight inference
engines using structured JSON responses.

The on-device Apple Foundation Model identified only
one of four seeded defects and produced two confidently
incorrect grammatical findings.

It also failed to identify either redundancy cluster
in the evaluation passage.

Its available context window was approximately
4,096 tokens.

The results demonstrated that the model was unsuitable
for the intended proofreading workflow.

Ollama-hosted models demonstrated substantially better
performance in the same preliminary evaluation.

==== Decision

Use local Ollama inference for the initial release.

The plugin shall connect to a configured loopback
Ollama endpoint.

Apple `fm` integration shall not be implemented
in the initial release.

==== Rationale

* Better preliminary language-review performance.
* Configurable model selection.
* Larger practical context options.
* Local processing without external API credentials.
* Existing Ollama installation on the target machine.
* No custom compiled inference helper.

==== Consequences

Positive::

* The plugin can use different local models.
* The inference interface is independent of macOS `fm`.
* Model upgrades do not require plugin redesign.
* Document contents remain local during inference.

Negative::

* Ollama must be installed and running.
* Models must be downloaded and managed.
* Memory and inference latency depend on model selection.
* Model quality remains probabilistic.

==== Validation

The Ollama endpoint, configured model and structured
output behaviour shall be checked before review.

The plugin shall fail visibly if the service or model
is unavailable.

=== ADR-015: Asynchronous Ollama HTTP Transport

Status:: Accepted
Date:: 2026-11-16
Supersedes:: ADR-003

==== Context

Model inference may take several seconds or longer.

Neovim must remain responsive.

The selected inference service exposes a local HTTP API.

==== Decision

Use asynchronous HTTP requests to Ollama.

The initial implementation may invoke `curl`
through `vim.system()`.

The adapter shall submit JSON request bodies and
receive complete JSON responses.

==== Rationale

* Avoids blocking Neovim.
* Uses native Neovim process management.
* Requires no additional Lua HTTP dependency.
* Supports timeouts and cancellation.
* Avoids placing document contents in shell arguments.

==== Consequences

The adapter must handle:

* Connection failures.
* HTTP errors.
* Timeouts.
* Cancellation.
* Invalid responses.
* Model unavailability.

No shell interpolation shall be used.

The controller shall prevent cancelled requests
from publishing results.

=== ADR-016: Structured Findings and Exact-Source Validation

Status:: Accepted
Date:: 2026-11-16
Revises:: ADR-004
Reinforces:: ADR-008

==== Context

Local model testing demonstrated that schema-constrained
generation does not guarantee exact source quotations.

Models sometimes returned entire paragraphs or code
blocks, combined independent defects or quoted text
that did not match the source exactly.

These failures undermine reliable quickfix navigation.

==== Decision

Use a versioned JSON Schema for model responses.

Apply deterministic validation to every finding before
creating a quickfix entry.

A finding shall be accepted only when:

* Its category is supported.
* Its original quotation matches the source exactly.
* Its source location can be resolved unambiguously.
* It does not overlap protected content.
* It belongs to the current buffer snapshot.

==== Rationale

* Prevents fabricated locations.
* Protects source navigation.
* Rejects malformed or unverifiable output.
* Separates model behaviour from editor correctness.

==== Consequences

Some potentially useful findings may be rejected.

The plugin shall report rejected-finding counts.

It shall not silently invent source coordinates.

Exact-source fidelity and finding granularity shall
be measured separately in model evaluations.

=== ADR-017: Restricted Proofreading Scope

Status:: Accepted
Date:: 2026-11-16

==== Context

The original concept included general editorial review,
ambiguity detection, repetition analysis and stylistic
consistency.

The intended primary use is narrower: correcting
spelling, grammar and punctuation in written prose.

The author also requires assistance with excessively
long or convoluted sentences.

Expanding into general editorial analysis would increase
complexity, latency and unwanted suggestions.

==== Decision

The initial release shall support exactly four
proofreading categories:

. Spelling.
. Grammar.
. Punctuation.
. Sentence readability and restructuring.

The sentence-readability category shall identify
unwieldy sentence construction and suggest improvements
without changing meaning.

==== Rationale

* Aligns with the actual user requirement.
* Avoids scope creep.
* Simplifies prompts and response validation.
* Reduces irrelevant findings.
* Makes model evaluation more focused.
* Keeps the implementation maintainable.

==== Consequences

The following are outside the initial scope:

* General stylistic rewriting.
* Independent ambiguity analysis.
* Independent repetition analysis.
* Logical consistency checking.
* Terminology consistency analysis.
* Document-wide rewriting.
* Fact-checking.

These capabilities shall not be introduced implicitly
through prompts or model configuration.

Any expansion requires an explicit scope decision.

=== ADR-019: Protect Markup Before Inference

Status:: Accepted
Date:: 2026-11-16
Reinforces:: ADR-010

==== Context

Local testing demonstrated that models may treat
AsciiDoc source blocks and structural syntax as prose.

Some models returned findings covering code blocks
or proposed corrections to valid markup.

Prompt instructions alone did not reliably prevent
these errors.

==== Decision

Protect non-prose content before submitting text
to the model.

Use format-aware exclusion or sentinel masking.

Preserve deterministic mappings to the original buffer.

==== Rationale

* Prevents inappropriate proofreading of code.
* Protects AsciiDoc structure.
* Reduces model distraction.
* Improves source-location reliability.
* Avoids relying solely on prompt compliance.

==== Consequences

Format adapters require dedicated tests.

If masking changes text length, explicit source
offset mapping is required.

Findings overlapping protected regions shall be rejected.

=== ADR-020: Separate Corrections and Sentence Rewrites

Status:: Superseded
Date:: 2026-11-16
Reinforces:: ADR-007
Superseded by:: ADR-028

==== Context

Spelling, grammar and punctuation errors usually
require localised corrections.

Unwieldy sentence construction may require replacing
or dividing an entire sentence.

These are different kinds of finding and should not
be presented as equivalent errors.

==== Decision

Support two logical finding types.

Correction::
A localised spelling, grammar or punctuation issue.

Sentence rewrite::
An advisory replacement for a complete sentence
whose construction makes it unnecessarily difficult
to read.

Both shall use the same quickfix interface.

==== Rationale

* Preserves finding granularity.
* Distinguishes errors from suggestions.
* Supports accurate source navigation.
* Avoids unnecessary rewriting.
* Maintains authorial control.

==== Consequences

Sentence rewrites shall quote the complete
original sentence.

Length alone shall not trigger a finding.

Rewrites shall preserve meaning, factual detail,
technical terminology and authorial voice.

No suggested correction or rewrite shall be
applied automatically.

=== ADR-021: Machine-Checkable Response Contract

Status:: Accepted
Date:: 2026-11-16
Refines:: ADR-016, ADR-020
Revised by:: ADR-026, ADR-028

==== Context

ADR-016 introduced a versioned findings schema and
deterministic source validation.

ADR-020 introduced two finding types.

Both are described in the design guide as prose.

Neither has been fixed in a form that can be
implemented or tested without interpretation.

Four ambiguities remain:

* No response field distinguishes a correction from a
  sentence rewrite.
* `severity` appears in the internal representation but
  is never supplied by the model.
* Repeated quotations are handled by an optional
  mechanism rather than a fixed rule.
* Hard-wrapped source lines make exact quotation
  unreliable across a line break.

Without a resolution, the validator has no defined
behaviour for the common failure cases, and model
evaluation has no stable target.

==== Decision

The following contract is normative.

===== Request Conditions

A review request shall:

. Use the configured loopback Ollama endpoint.
. Post to `/api/generate`.
. Set `stream` to `false`.
. Set `options.temperature` to `0`.
. Set `format` to the packaged JSON Schema.
. Set `think` to `false` where the model supports it.

The `response` field of a successful reply contains a
JSON string, which shall be decoded.

If decoding yields a further string, it shall be
decoded once more.

Further nesting, a missing field, an empty field or a
decode failure shall fail the chunk.

An empty response shall never be read as an absence
of findings.

===== Response Envelope

The decoded object contains one required key,
`findings`, which may be an empty array.

[source,json]
----
{
  "findings": [
    {
      "type": "correction",
      "category": "spelling",
      "original": "recieved",
      "suggestion": "received",
      "message": "Incorrect spelling."
    }
  ]
}
----

No other top-level key is permitted.

The schema version is a plugin concern and shall not
be supplied by the model.

===== Finding Fields

[cols="1,1,3",options="header"]
|===
|Field |Required |Constraint

|`type`
|Yes
|`correction` or `rewrite`.

|`category`
|Yes
|`spelling`, `grammar`, `punctuation` or
`sentence_readability`.

|`original`
|Yes
|Non-empty exact quotation from the reviewed text.

|`suggestion`
|Yes
|Non-empty replacement text.

|`message`
|Yes
|Non-empty single-sentence explanation.
|===

===== Type and Category Coupling

`rewrite` shall be used only with
`sentence_readability`.

`correction` shall be used only with `spelling`,
`grammar` or `punctuation`.

A finding that breaks this coupling is rejected.

===== Severity Derivation

Severity is derived by the plugin and is never read
from the model response.

`correction` findings use quickfix severity `warning`.

`rewrite` findings use quickfix severity `info`.

===== Locating Rules

A finding is located within the reviewable text of the
chunk that produced it.

The quotation shall match exactly, including case,
punctuation and internal spacing.

A finding is accepted only when the quotation occurs
exactly once in that reviewable text.

A quotation that occurs more than once is rejected as
ambiguous.

The validator shall neither choose an occurrence nor
widen the search to the whole buffer.

===== Whitespace Fallback

Prose is hard-wrapped, so a sentence spanning two
source lines contains a newline in the reviewable
text.

If the exact match fails, one further pass is
permitted.

In that pass, runs of whitespace in both the quotation
and the reviewable text collapse to a single space
before comparison.

The pass succeeds only when it produces exactly one
match.

Every collated character shall retain a mapping to its
original byte offset, so that the resulting quickfix
position is derived from the original buffer.

No other normalisation is permitted.

Case folding, Unicode normalisation, smart-quote
substitution and typographic equivalence shall not be
applied.

===== Rejection Reporting

Every rejected finding shall be counted against
exactly one reason.

[cols="1,3",options="header"]
|===
|Reason |Condition

|`schema_invalid`
|The envelope or an object fails the schema.

|`not_exact`
|The quotation does not match the reviewable text.

|`not_unique`
|The quotation matches more than once.

|`protected`
|The quotation overlaps protected content.

|`unsupported_category`
|The category is outside the four agreed categories.

|`type_mismatch`
|`type` and `category` are inconsistently paired.

|`no_change`
|The suggestion is identical to the quoted or source text.

|`stale`
|The finding belongs to a superseded review.
|===

==== Rationale

* Removes the remaining interpretative gaps.
* Makes every rejection reason testable.
* Keeps severity and coordinates under plugin control.
* Refuses to guess when a quotation is ambiguous.
* Limits whitespace tolerance to the single case the
  source format forces.
* Gives the benchmark a stable contract to measure.

==== Consequences

Short quotations without surrounding context are more
likely to be rejected as ambiguous.

Model evaluation shall report exact-quote accuracy
against this contract rather than against a looser
reading of the design guide.

The optional repeated-quotation wording in the design
guide is superseded.

The schema shall be shipped as one versioned artefact
and tested against the examples in this record.

The whitespace fallback shall be bounded to one extra
scan per chunk.

=== ADR-026: Expanded Proofreading Scope

Status:: Superseded
Date:: 2026-11-17
Supersedes:: ADR-017
Revises:: ADR-021
Superseded by:: ADR-028

==== Context

ADR-017 limited the initial release to spelling,
grammar, punctuation and sentence readability.

The intended proofreading workflow also needs to find
common problems with sentence structure, inappropriate
word choice and inconsistent usage within a document.

These checks remain narrower than general stylistic
editing, ambiguity analysis, logical review or
fact-checking.

ADR-021 fixed a response schema whose category enum and
type coupling reflected the four-category scope.

==== Decision

The plugin shall support seven proofreading categories:

. `spelling`.
. `grammar`.
. `punctuation`.
. `sentence_readability`.
. `structure`.
. `word_choice`.
. `consistency`.

`structure` covers a sentence whose arrangement of
clauses or phrases impairs comprehension even when its
individual words and grammar are valid.

`word_choice` covers a locally inappropriate, commonly
confused or contextually incorrect word where a specific
replacement preserves the author's intended meaning.

`consistency` covers inconsistent spelling, capitalisation,
hyphenation or terminology within the reviewed document.
It does not establish a project terminology policy or
perform logical consistency analysis.

`sentence_readability` and `structure` use finding type
`rewrite` and shall quote a complete source sentence.

`spelling`, `grammar`, `punctuation`, `word_choice` and
`consistency` use finding type `correction`.

The packaged JSON Schema and deterministic validator
shall enforce these seven categories and their type
coupling.

==== Rationale

* Captures common proofreading problems that are not
  represented by the original four categories.
* Keeps each finding tied to an exact source quotation
  and a concrete suggested replacement.
* Separates sentence construction from general
  readability while retaining advisory severity.
* Limits consistency checking to observable document
  usage rather than broader editorial policy.
* Preserves the exclusion of unrestricted style review.

==== Consequences

The prompt, schema, validator, quickfix presentation and
benchmark corpus shall use the seven-category enum.

Consistency findings may require surrounding or
document-level context to establish the preferred form.
The implementation shall still locate and report one
exact source occurrence per finding.

General stylistic rewriting, ambiguity analysis,
redundancy analysis, logical consistency checking,
terminology-policy enforcement and fact-checking remain
outside scope.

=== ADR-028: Three-Category Correction Scope

Status:: Accepted
Date:: 2026-11-17
Supersedes:: ADR-020, ADR-026
Revises:: ADR-021

==== Context

ADR-026 expanded the plugin from four proofreading
categories to seven.

That expansion moved the product beyond its useful core.
Sentence readability, structure, word choice and
consistency invite subjective editorial changes rather
than bounded mechanical corrections.

The intended workflow is limited to spelling, grammar and
punctuation.

ADR-020 and ADR-021 also provided for sentence rewrites,
which are no longer required.

==== Decision

The plugin shall support exactly three categories:

. `spelling`.
. `grammar`.
. `punctuation`.

Every accepted finding shall have type `correction`.

The packaged JSON Schema shall permit only those three
categories and the `correction` type.

Sentence readability, sentence restructuring, general
structure analysis, word-choice review and consistency
review are outside scope.

The prompt, validator, quickfix presentation, fixtures and
benchmark shall use the three-category contract.

==== Alternatives Considered

Keep four categories::
Retaining sentence readability would preserve the original
rewrite workflow, but would continue subjective editorial
behaviour that is no longer wanted.

Keep seven categories but disable four by default::
This would retain unnecessary schema, prompt, validation and
test complexity, and would make future scope drift easier.

Use configurable arbitrary categories::
This would weaken deterministic validation and make model
behaviour harder to evaluate.

==== Rationale

* Matches the revised product intent exactly.
* Removes subjective sentence rewriting.
* Simplifies prompts, schema validation and evaluation.
* Reduces unwanted findings and implementation complexity.
* Keeps every finding suitable for a bounded replacement.

==== Consequences

ADR-026 remains as historical evidence of the abandoned
scope expansion.

The `rewrite` finding type and informational quickfix
severity are removed from the current design.

The schema retains the `type` field for an explicit,
machine-checkable contract, but its only valid value is
`correction`.

Any future category requires a new accepted ADR.

=== ADR-029: Explicit Correction Application

Status:: Accepted
Date:: 2026-11-17
Supersedes:: ADR-007
Revises:: ADR-025

==== Context

ADR-007 prohibited all source-buffer modification and
required authors to reproduce corrections manually.

Every accepted finding now represents a validated,
localised replacement with exact original and suggested
text.

The author needs to apply either the current recommendation
or all recommendations without retyping them.

Model suggestions remain untrusted, and edits may occur
between review and application.

==== Decision

Provide two explicit, user-triggered operations:

Individual application::
Apply the validated correction represented by the current
quickfix entry.

Bulk application::
Apply all unapplied validated corrections from the latest
published review.

Expose these operations through `apply()` and `apply_all()`
in the public Lua API and through
`:AIProofreadApply` and
`:AIProofreadApplyAll`.

Review completion shall never apply a correction by itself.

Each published correction shall retain its verified source
range, exact source slice and a Neovim extmark that tracks
the range through intervening edits.

Immediately before an individual edit, the plugin shall
verify that the tracked range still contains the exact
source slice captured by deterministic validation.

Bulk application shall:

. Resolve all unapplied corrections from the latest review.
. Verify every current range and exact source slice.
. Reject duplicate or overlapping ranges.
. Complete the full preflight before modifying the buffer.
. Abort without changes if any preflight check fails.
. Apply replacements from the end of the buffer backwards.
. Join all replacements into one Neovim undo step.

An applied correction shall not be applied again.

==== Alternatives Considered

Keep manual editing only::
This preserves the strongest non-destructive rule but adds
avoidable friction and transcription errors.

Apply each finding as soon as it is produced::
This removes authorial review, risks unwanted changes and
mixes probabilistic inference with editor mutation.

Apply all valid findings and skip stale ones::
This can leave a partially corrected document while
appearing to have completed one bulk action.

Re-run source searches during application::
This could select a different repeated occurrence and
would weaken the exact verified-range guarantee.

==== Rationale

* Keeps every edit under explicit author control.
* Reuses deterministic validation already required for
  quickfix navigation.
* Prevents stale or ambiguous replacements.
* Gives bulk application atomic user-visible semantics.
* Preserves easy recovery through a single undo step.
* Allows individual edits without retyping model output.

==== Consequences

The runtime design gains a correction-applier component and
state linking quickfix entries to validated findings.

Extmarks are an editor-tracking aid, not sufficient proof
that a correction remains valid. Exact source-slice
verification is still mandatory immediately before
replacement.

After any application, the original review is no longer a
complete representation of the buffer. Unapplied findings
may continue to be used only while their tracked ranges and
exact source slices remain valid.

Bulk preflight failure shall report the reason and leave the
buffer unchanged.

Tests shall cover individual application, atomic bulk
application, overlap rejection, stale text, extmark movement,
duplicate application prevention and single-step undo.

=== ADR-030: Dismiss Individual Recommendations

Status:: Accepted
Date:: 2026-11-18
Refines:: ADR-029

==== Context

Not every valid recommendation should be applied.

Leaving a rejected recommendation in quickfix makes it
difficult to distinguish outstanding work from an item the
author has already considered.

==== Decision

Provide `ignore()` in the public Lua API and
`:AIProofreadIgnore` as a user command.

Ignoring shall:

. Leave the source buffer unchanged.
. Mark the current finding as ignored.
. Remove its extmark and quickfix entry.
. Select the next outstanding quickfix entry.
. Exclude the finding from subsequent bulk application.

A new review may report the same issue again.

==== Rationale

* Treats quickfix as a queue of outstanding recommendations.
* Preserves authorial control without retaining resolved
  workflow items.
* Keeps ignored findings out of bulk application.
* Requires no persistent dictionary or suppression policy.

==== Consequences

Ignore state lasts only for the current published review.

The plugin does not maintain a permanent ignore list.

Tests shall verify that ignoring changes neither source text
nor undo history, advances quickfix and excludes the finding
from bulk application.

=== ADR-031: Exact Visual-Selection Review

Status:: Accepted
Date:: 2026-11-18
Refines:: ADR-010, ADR-011

==== Context

Complete-buffer review can be unnecessarily slow when the
author wants feedback on only a small passage.

Visual selections must retain original-buffer coordinates so
that quickfix navigation and correction application remain
safe.

==== Decision

Provide `review_selection()` in the public Lua API,
`:AIProofreadSelection` as a command and a visual-mode
review keymap.

Characterwise and linewise selections shall be supported.
Blockwise selections shall fail visibly because they are not
a contiguous source range.

The controller shall review only the selected byte range
while retaining the complete buffer snapshot for markup
protection, coordinate calculation and stale-result checks.

==== Rationale

* Reduces inference work for focused proofreading.
* Preserves exact original-buffer coordinates.
* Reuses the existing review, validation and quickfix path.
* Avoids ambiguous semantics for discontiguous block ranges.

==== Consequences

Any change to the buffer while selection review is running
shall invalidate the result.

Selection boundaries are byte-oriented and shall include the
complete final UTF-8 character.

Tests shall cover exact submitted text and absolute quickfix
coordinates.

=== ADR-032: Asynchronous Model Preload

Status:: Accepted
Date:: 2026-11-18
Refines:: ADR-014, ADR-015, ADR-025

==== Context

The first review may be delayed while Ollama loads the model.

The target environment may already use
`OLLAMA_KEEP_ALIVE` to control model residency.

Neovim startup must not wait for model loading.

==== Decision

Add `ollama.preload`, defaulting to `false`.

When enabled, `setup()` shall start an asynchronous
`POST /api/generate` request containing the configured model,
`stream: false` and no prompt.

Add optional `ollama.keep_alive`.
When supplied, it shall be sent with preload and review
requests.
When omitted, Ollama's configured `OLLAMA_KEEP_ALIVE`
behaviour shall remain in effect.

Preload failure shall produce a warning but shall not prevent
Neovim startup or later review attempts.

==== Rationale

* Reduces first-review latency.
* Does not block Neovim startup.
* Complements existing Ollama residency configuration.
* Keeps preloading explicitly opt-in because it consumes
  memory before the first review.

==== Consequences

Enabling preload may cause immediate CPU, GPU and memory use
when Neovim starts.

The plugin shall not download a missing model.

Health checking remains the explicit way to diagnose service
or model availability.

Tests shall verify asynchronous invocation, keep-alive
propagation and non-generating preload payloads.

=== ADR-034: Selectable fm and Ollama Backends

Status:: Accepted
Date:: 2026-11-18
Supersedes:: ADR-014
Refines:: ADR-013, ADR-015, ADR-018

==== Context

Ollama with Gemma provides better proofreading quality but
requires installation and a model download.

Current macOS systems provide the native `fm` command and an
on-device Apple Foundation Model with no Ollama dependency.
Earlier testing found that model less accurate, but it is
fast and lowers the barrier to trying the plugin.

Support two configured local inference backends:

`ollama`::
The default, higher-quality backend using the existing local
HTTP integration and configurable model.

`fm`::
An optional zero-download backend using

* Provides an immediate native trial path on supported Macs.
* Retains Ollama and Gemma for better proofreading quality.
* Keeps all inference local.
* Contains provider-specific transport behind adapters.
* Prevents lower-quality model output bypassing validation.

==== Consequences

The configuration gains `backend`, `fm` and `ollama`
sections.

The health check validates only the selected backend.

Ollama preload and keep-alive settings do not apply to `fm`.

The documentation shall state clearly that `fm` has lower
proofreading accuracy.

=== ADR-035: Streaming Findings and Rebase on Apply

Status:: Accepted
Date:: 2026-11-18
Supersedes:: ADR-011
Refines:: ADR-005, ADR-027, ADR-029, ADR-030

==== Context

The controller already processes chunks sequentially and validates
each response before advancing.

It published the complete quickfix list only after the final chunk.
Time to the first finding was therefore the sum of all chunk
latencies.

ADR-011 required stale results to be discarded because no result
was visible until the review finished.

Streaming changes that condition.

Findings, extmarks and quickfix entries are live while later
chunks are still being reviewed.

An explicit correction application changes the buffer during that
window.

==== Decision

The controller shall publish each chunk's validated findings as
soon as that chunk completes.

Findings shall be sorted within the chunk and appended to the
existing AI Proofread quickfix list.

The controller shall never rebuild the list from its accumulator,
so entries removed by apply or ignore are not restored.

When `quickfix.auto_open` is enabled, the quickfix window shall
open on the first published finding.

The source window and cursor shall be restored after opening.

The quickfix title shall remain `AI Proofread`.

Progress and completeness shall be reported through quickfix
context instead.

Finding identifiers shall come from a monotonically increasing
published count so they remain stable across appends.

Correction registration shall be additive.

Starting a new review or cancelling an active one shall clear the
extmarks, correction state and quickfix entries belonging to the
superseded review.

Ignoring leaves the buffer unchanged.

The review shall continue and later findings shall append
normally.

Applying a correction does change the buffer.

Only already published findings can be applied, so every edit lies
at or before the currently reviewed chunk.

The controller shall record the byte and line deltas of each
plugin originated edit.

It shall rebase the absolute source offsets and protected spans
of pending chunks by those deltas, update their snapshot reference
and advance its baseline changedtick.

Published quickfix positions shall be refreshed from extmarks,
which already track the edit.

Review shall then continue.

Any other buffer change shall invalidate the review.

The controller shall stop outstanding work, remove that review's
published entries and extmarks, and report the review as stale.

Cancellation shall remove the same artefacts.

The `complete` context flag shall remain false until every chunk
has returned or failed.

Validation, source coordinates and finding categories are
unchanged by this decision.

Bounded concurrency remains out of scope.

==== Rationale

Publishing per chunk reduces time to the first useful finding
without changing inference order.

Appending rather than rebuilding keeps authorial actions intact
while the review is still running.

Extmarks already follow intervening edits, so they are the
authoritative source for refreshed quickfix positions.

Exact source slice verification in `apply` still guards every
edit.

Rebasing is safe because applied findings can only come from
earlier chunks, making every affected edit precede the pending
source ranges.

==== Consequences

ADR-011's discard rule is superseded only for buffer changes
caused by the plugin's own apply operation.

External edits still discard the review.

The `review.max_concurrent` setting remains reserved for a later
decision and has no runtime effect.

Tests shall cover incremental publication, stable identifiers,
apply and ignore during review, rebasing after edits, stale
external changes and cancellation cleanup.

=== ADR-036: Long-Sentence Detection and Rewrites

Status:: Accepted
Date:: 2026-11-23
Supersedes:: ADR-028
Refines:: ADR-016, ADR-020, ADR-021, ADR-029

==== Context

ADR-028 restricted proofreading to spelling, grammar and
punctuation because general readability and stylistic
rewrites were too subjective.

Repeated use has identified one narrower requirement:
sentences over a configured word limit are a recurring
authoring problem and benefit from an applicable quickfix
suggestion.

The boundary can be deterministic even though producing a
useful split requires the selected local model.

Whole-sentence rewrites can overlap local spelling, grammar
or punctuation corrections.

Publishing both would make bulk application fail its overlap
preflight and would create competing recommendations.

==== Decision

Add `long_sentence` as a fourth, enabled-by-default check.

Its configured `max_words` shall default to 30.
A finding qualifies only when the validated source quotation
contains more than that number of words.

The model shall quote the complete sentence and return a
`rewrite` finding whose suggestion splits it into shorter
sentences.

The suggestion shall preserve meaning, factual detail and
authorial voice.
It shall not remove content merely to make the result
shorter.

The validator shall:

. Locate the quoted sentence using the existing exact-source
  rules.
. Count words in the validated source slice.
. Reject a `long_sentence` finding at or below the configured
  threshold.
. Reject a rewrite that does not change the validated source
  slice.
. Prefer a validated long-sentence rewrite over spelling,
  grammar or punctuation findings wholly contained within
  its source range.

The quickfix and application workflows shall treat the
validated rewrite like another applicable finding.

General readability, ambiguity, redundancy, logic,
terminology consistency and unrestricted stylistic rewriting
remain outside scope.

==== Rationale

A deterministic threshold keeps detection predictable and
configurable.

Limiting the suggestion to a meaning-preserving split
addresses the observed problem without reopening general
style editing.

Giving the whole-sentence rewrite precedence avoids
overlapping quickfix entries and preserves atomic bulk
application.

==== Consequences

The response schema gains the `long_sentence` category and
the `rewrite` type.

Configuration gains `checks.long_sentence` and
`long_sentence.max_words`.

Prompt instructions must distinguish local corrections from
whole-sentence rewrites.

Tests shall cover threshold enforcement, disabled checks,
meaning-preserving prompt instructions and overlap
precedence.

=== ADR-037: Harden Rewrite and Transport Trust Boundaries

Status:: Accepted
Date:: 2026-11-23
Refines:: ADR-008, ADR-016, ADR-019, ADR-034, ADR-036

==== Context

ADR-036 validates the word count of a model-supplied
quotation, but that alone does not prove that the quotation
is one complete sentence or that the suggestion splits it.

Model responses also require explicit size limits.
The local-only privacy promise requires enforcement rather
than documentation alone.

==== Decision

The plugin shall detect long-sentence candidates in code
before inference.
The model may rewrite only those exact candidates.

A rewrite shall contain at least two sentences, each within
the configured word limit.
Control characters other than ordinary whitespace shall be
rejected.

Response bytes, finding counts and finding field lengths
shall have fixed upper bounds before editor state is created.

Ollama endpoints shall use `localhost`, `127.0.0.1` or
`[::1]`.
Remote endpoints shall be rejected without an override.

Quickfix presentation shall target the global quickfix
window explicitly and shall not configure a location-list
window.
Source preview shall use the review's originating window
rather than an arbitrary split.

==== Rationale

These checks convert prompt instructions into enforceable
boundaries, limit denial-of-service exposure and preserve the
plugin's local privacy guarantee.

==== Consequences

Sentence detection becomes a shared code module used by
prompt construction and validation.

Some ambiguous prose and abbreviations may remain unsuitable
for automatic rewriting and shall be rejected safely.

Tests shall include hostile rewrites, oversized output,
location-list coexistence and malformed configuration.

=== ADR-038: Preserve Streaming with Bounded Rewrite Retries

Status:: Accepted
Date:: 2026-11-23
Refines:: ADR-035, ADR-036, ADR-037

==== Context

Streamed publication depends on each chunk callback reaching
quickfix before later chunks are submitted.

The first long-sentence implementation enumerated code-detected
candidates in the general prompt.

Repeated local testing showed that the default model sometimes
copied a candidate into both `original` and `suggestion`.

Safe validation rejected that rewrite, so no quickfix entry was
published for the candidate.

A general retry could multiply requests without bound or widen
the category scope.

==== Decision

The general prompt shall describe the long-sentence category
without embedding the candidate list.

Deterministic candidates shall remain the only sentences that
validation accepts for rewrite.

When a candidate's first rewrite is rejected solely as a no-op
or an invalid bounded split, the controller shall issue at most
one focused retry for that candidate.

Retries shall use a narrow response contract that permits one
`rewrite` finding in the `long_sentence` category.

The number of retries per chunk shall be bounded.

Valid findings shall be published before retries start.

The next chunk shall start only after retries finish.

The progress count shall report the number of chunks actually
processed.

==== Rationale

The focused prompt removes the copying pattern observed with a
large candidate array without weakening source validation.

Publishing before retry preserves the visible streaming
behaviour defined by ADR-035.

A bounded retry set limits latency and request cost while
recovering the common malformed-output case.

==== Consequences

Both Ollama and `fm` gain a second packaged response schema for
rewrite retries.

Quickfix context reaches `chunks_total` exactly once when the
review completes.

Tests shall cover focused retry payloads, bounded retry
selection, unchanged streaming and final progress counts.

=== ADR-039: Bound fm Chunks and Report Review Progress

Status:: Accepted
Date:: 2026-11-23
Refines:: ADR-034, ADR-035, ADR-037

==== Context

The `fm` backend was tested with the default 2,500-byte review
chunk on local prose.

The plugin issued three requests, but the first structured
request spent roughly 67 seconds before failing with a context
size error.

A manual unstructured `fm` response completed in a few seconds.

Reduced chunk sizes produced structured responses in
single-digit seconds, with an 800-byte budget returning the
first result in about 6.5 seconds.

Quickfix remained empty until the first validated chunk, so a
slow request looked like an unresponsive plugin.

==== Decision

The `fm` backend shall use a separate `fm.chunk_size`
configuration value with a default of 800 bytes.

Ollama shall continue to use `review.chunk_size`.

The controller shall select the chunk budget from the active
backend before preparing review chunks.

The plugin shall emit one in-place Neovim progress message at
review start.

That message shall refresh on a timer and report the backend,
chunk position, phase and elapsed time.

Final progress state shall report success, failure or
cancellation.

The plugin shall expose `require("ai-proofread").status()` for
statusline integration.

==== Rationale

A smaller structured request fits the effective on-device
context and avoids the long failure path.

Visible progress distinguishes slow inference from an
unresponsive command and discourages repeated invocation.

A stable progress message avoids filling Neovim's message
history during long reviews.

==== Consequences

Configuration validation gains `fm.chunk_size` constraints.

A progress module owns the message lifecycle and timer.

Tests shall cover the backend-specific chunk budget,
validation, progress updates, final status and the status API.

=== ADR-040: Apply a Visual Quickfix Range

Status:: Accepted
Date:: 2026-11-25
Refines:: ADR-029, ADR-035

==== Context

Authors can apply one current finding or every outstanding
finding, but cannot choose a contiguous subset in quickfix.

The existing bulk path already preflights source ranges,
checks overlap, applies from the end and joins the edits.

==== Decision

An explicit range on `:AIProofreadApply` shall identify the
selected rows in the AI Proofread quickfix window.
Visual Line selection followed by the command shall pass
that range through Neovim's standard Ex command behaviour.

The command shall resolve each selected row by its immutable
finding identifier and reject unrelated lists, location
lists, source-buffer ranges and inactive findings.
All selected findings shall belong to one review and buffer.

The selected batch shall use the existing bulk preflight,
reverse-order edits and single undo step.
No selected entry shall be removed if preflight fails.
An un-ranged invocation shall retain its individual
application behaviour.
`:AIProofreadApplyAll` shall still apply all outstanding
findings.

==== Rationale

Reusing the verified bulk path preserves the source-match
and overlap guarantees without introducing a second editing
algorithm.
Restricting ranges to quickfix prevents document line numbers
from accidentally selecting unrelated corrections.

==== Consequences

The apply command accepts Ex ranges only in the AI Proofread
quickfix window.
User-facing documentation shall show Visual Line mode and the
explicit command.
Tests shall cover subset selection, unchanged findings,
atomic preflight and one undo step.

* Review latency on representative documents.
* Handling of partially failed reviews.
* Public distribution and dependency documentation.

These shall be resolved before the first public release.

== Scope Control

The project shall remain focused on:

* British English spelling.
* Grammar.
* Punctuation.

New editorial capabilities require a separate,
explicitly accepted architectural decision.

The presence of a capable language model does not
constitute a requirement to use its other capabilities.
